# 실행 영수증 · 산출물과 검토를 같은 버전에 묶는다

> 업무 한 건마다 산출물 폴더에 실행 영수증 하나를 둔다. 첫 실행은 `run.json`, 같은 폴더의
> 두 번째 실행은 `run-2.json`이다. 원장은 사람이 읽는 기록이고,
> 이 파일은 기계가 대조하는 증거다. **원장을 대체하지 않는다.**

## 왜 필요한가

`gate.md`가 있어도 그 뒤에 본문을 고치면, 검토한 문장과 전달할 문장이 달라진다.
`run.json`은 입력·프로필·스킬·산출물·검토 보고서의 SHA-256을 묶어 다음을 가른다.

- 어떤 자료와 스킬 버전으로 만들었는가
- AI 사업검토자·AI 규제검토자가 정확히 어느 산출물을 봤는가
- 검토 뒤 산출물이나 보고서가 바뀌었는가
- 원장에 같은 실행이 실제로 남았는가

⛔ 원문 데이터나 개인정보를 복사하지 않는다. **경로·기간·파일 지문만** 적는다.

## 0. 계획이 먼저다 · `plan.json`

`run.json` 보다 앞에 같은 폴더의 `plan.json` 이 온다. 승인의 대상은 **문장이 아니라 해시**다.

```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/plan-compiler.mjs" compile "outputs/{날짜}/{번호}-{슬러그}/plan.json"
# 사용자가 「진행 승인」이라고 답한 뒤
node "${CLAUDE_PLUGIN_ROOT}/scripts/plan-compiler.mjs" approve "outputs/{날짜}/{번호}-{슬러그}/plan.json"
```

`plan.json` 이 있으면 `run-receipt start` 가 **승인 해시·스킬 순서·산출물·검토를 대조**한다.
하나라도 다르면 실행을 열지 않는다. 계획을 고쳤으면 `compile` 부터 다시 하고 새로 승인받는다.
`plan.json` 이 없으면 예전 경로 그대로 간다.

---

## 0-b. 단계가 여럿이면 한 단계씩 여닫는다

`plan.json` 에 `steps` 가 있으면 `start` 가 그 구조를 영수증으로 옮긴다.
단계마다 `pending → running → completed` 이고, **완료 시점에 그 단계가 먹은 앞 산출물의 지문**을 남긴다.

```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/run-receipt.mjs" step-start "{run.json}" --step 1
# … 그 단계의 산출물을 만든 뒤
node "${CLAUDE_PLUGIN_ROOT}/scripts/run-receipt.mjs" step-done  "{run.json}" --step 1
```

- 앞 단계가 안 끝났는데 뒤 단계를 열면 막는다.
- 산출물이 실제로 없으면 `step-done` 이 막는다.
- 단계가 남았는데 `finalize --status completed` 하면 막는다.

**중단됐으면 처음부터 다시 만들지 않는다.**

```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/run-receipt.mjs" resume "{run.json}"
#  ▶ 재개 지점 · 단계 3 (스킬 065) · 이미 끝난 단계 1 · 2 는 다시 만들지 않습니다
```

`resume` 은 완료한 단계가 먹은 앞 산출물의 지문을 지금 값과 대조한다.
**바뀐 것을 먹는 단계와 그 뒤만** `pending` 으로 되돌린다 — 무관한 단계는 살려 둔다.

> 실측 2026-08-30 · 2단계 산출물(073)을 고치니 그것을 먹는 **4단계만** 되돌아갔다.
> 073 을 안 먹는 3단계는 `completed` 로 남았다.

## 1. 실행 전 · 뼈대를 먼저 쓴다

산출물 경로를 정한 직후, 같은 폴더에 아래 뼈대로 `run.json`을 쓴다.
같은 날 같은 스킬을 다시 실행해 산출물이 `-2`면 영수증도 `run-2.json`으로 맞춘다.
경로는 작업 폴더면 `workspace:`, 플러그인 샘플이면 `plugin:`으로 시작한다.

```json
{
  "schema": "marketing-team.run/v1",
  "status": "draft",
  "request": "사용자의 요청 원문",
  "skills": ["043"],
  "data_mode": "실데이터",
  "inputs": [
    { "path": "workspace:inputs/광고-브리프.md", "period": "2026-08-01~2026-08-30" }
  ],
  "profile": "workspace:brand/profile.md",
  "outputs": [
    "workspace:outputs/2026-08-30/043-meta-ad-copy/043-meta-ad-copy.md"
  ],
  "required_reviews": [],
  "reviews": [],
  "ledger": { "path": "workspace:logs/build-log.md" }
}
```

- `skills`는 실행 순서대로 적는다. 조합이면 `["061", "073", "065", "066"]`이다.
- `outputs`는 선택한 스킬들의 `writes_to`에 선언된 파일을 빠짐없이 적는다. 임의 파일은 추가하지 않는다.
  단일 스킬은 정본 경로를 그대로 쓰고, 조합은 선언된 **파일명**을 마지막 주 스킬 폴더에 모은다.
  `start`가 누락·추가 파일과 다른 폴더를 거부한다.
- **`pii: true` 스킬을 돌리면 `pii` 블록을 반드시 넣는다** (006·032·054·064·065·070·078·080).
  블록이 없거나 `pii.source`가 `inputs`에 없으면 `start`가 거부한다.

```json
  "pii": {
    "source": "plugin:sample-data/A브랜드-고객마스터.csv",
    "id_columns": ["고객ID"],
    "surrogate_column": "대체키"
  }
```

  `finalize` 와 `verify` 가 `scripts/pii-check.mjs` 를 함께 돌려 셋을 잰다.

  | 검사 | 걸리면 |
  |---|---|
  | 원문 식별자가 산출물·**검토 보고서**에 인용됐는가 | 🔴 완료 불가 |
  | 대체키가 원문에서 유도되는가 (해시 앞자리·base64·hex) | 🔴 완료 불가 |
  | 원문과 대체키가 같은 줄에 남았는가 (대응표 저장) | 🔴 완료 불가 |

  대체키는 **실행마다 만든 임의값**이어야 한다. 무염 해시 앞자리는 원문 공간이 작으면
  전수 대입으로 복원된다 — 실측에서 880개가 1초 만에 되돌아왔다.
  검토 보고서도 검사 대상이다. 산출물을 고쳐도 **검토자가 원문을 되풀이하면 다시 샌다.**
- `required_reviews`는 비워도 된다. `start`가 `review:`와 `gate:` 정본을 읽어 **산출물별로 자동 생성**한다.
  수동 항목을 더하면 자동 항목과 합쳐지고 중복은 제거된다. 발행물 셋이면 규제 검사도 셋이다.
- 프로필 대신 샘플을 썼으면 `plugin:sample-data/profile-sample.md`로 적는다.
- 입력 기간이 없으면 지어내지 않고 `미확인`이라고 적는다.

초안을 쓴 다음 봉인한다. 사용자 요청문은 셸 인수로 넘기지 않는다.

```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/run-receipt.mjs" start "outputs/{날짜}/{번호}-{슬러그}/run.json"
```

`start`부터 단계·검토·완료까지의 전이는 `logs/orchestrator-events.jsonl`에 자동 기록된다.
한 실행의 흐름은 다음 명령으로 요약한다.

```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/orchestrator-events.mjs" summary "logs/orchestrator-events.jsonl" "{run_id}"
```

도구 호출 수를 아는 실행기는 중간에 사용량을 더할 수 있다. 시간과 검토 라운드는 자동으로 갱신된다.
현재 예산은 소프트 경고이며, 충분한 실측 P95가 쌓이기 전에는 임의의 하드 상한을 두지 않는다.

```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/run-receipt.mjs" metric "{run.json}" --tool-calls 1
```

## 2. 검토 직후 · 본문 지문을 붙든다

AI 사업검토자나 AI 규제검토자가 보고서를 파일로 남긴 직후 AI 마케터가 실행한다.
**수정 전 검토가 조건부·반려면 먼저 고치고 다시 검토한 뒤 마지막 판정만 봉인한다.**

```bash
# 사업 검토
node "${CLAUDE_PLUGIN_ROOT}/scripts/run-receipt.mjs" review "{run.json}" \
  --kind business --perspective 재무 --status approved \
  --report "{review-재무.md}" --artifact "{산출물}"

# 규제 검사
node "${CLAUDE_PLUGIN_ROOT}/scripts/run-receipt.mjs" review "{run.json}" \
  --kind compliance --status pass \
  --report "{gate.md}" --artifact "{산출물}"
```

| 검토 | 허용 상태 |
|---|---|
| 사업 | `approved` · `conditional` · `rejected` |
| 규제 | `pass` · `needs-fix` · `blocked` · `industry-required` |

`completed`로 끝낼 수 있는 것은 사업 검토 `approved`, 규제 검사 `pass`뿐이다.

⛔ `verify`는 `completed`이면서 `integrity.status: current`, `completed_at`이 있는 영수증만 통과시킨다.
`running`·`pending`·`blocked`·`interrupted`는 현재 파일이 멀쩡해도 완료 검증 성공이 아니다.

## 3. 원장 뒤 · 마지막으로 완료를 봉인한다

산출물·검토 보고서·원장 1행이 모두 생긴 뒤 실행한다.

```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/run-receipt.mjs" finalize "{run.json}" --status completed
```

상태는 `completed` · `blocked` · `interrupted` · `save-failed` 중 하나다.
완료 전에 다음을 다시 계산한다.

1. 산출물 파일이 실재하는가
2. 검토할 때의 산출물 지문과 지금 지문이 같은가
3. 필수 검토가 최종 통과 상태인가
4. 원장에 산출물 경로나 `run_id`가 남았는가

하나라도 다르면 `verification-failed`로 남고 완료되지 않는다. 고친 뒤 재검토하고 다시 봉인한다.

지난 실행을 다시 쓸 때는 먼저 확인한다.

```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/run-receipt.mjs" verify "{run.json}"
```

## 4. 터미널이 없는 환경

`run.json` 뼈대까지는 파일로 남기되 아래를 덧붙인다.

```json
"integrity": {
  "status": "unverified-no-shell",
  "verified_at": null,
  "issues": ["파일 지문을 계산할 실행 도구가 없음"]
}
```

- G4에서 **「실행 기록은 남겼지만 파일 지문은 확인하지 못했습니다」**라고 한 줄 밝힌다.
- 대외 발행물은 오래된 `gate.md`를 재사용하지 않고, 현재 산출물 전문을 AI 규제검토자에게 다시 보낸다.
- `✅ 실행 영수증 확인`이라고 쓰지 않는다. 확인하지 않은 것은 확인했다고 말하지 않는다.

## 5. 차단된 실행도 근거를 잃지 않는다

⛔ 규제 차단이면 원장의 산출물 경로 칸에 `(차단됨)`만 쓰지 않는다.
`outputs/.../run.json (차단됨)`처럼 해당 실행 영수증 경로를 함께 적는다. 반복 실행이면
`run-2.json`처럼 실제 순번을 쓴다. 그래야 무엇을 검사해 막았는지 찾을 수 있다.
