# Claude Code 실기 검증 가이드

> 관련 문서: [런타임 안정성 수정 내역](./런타임-안정성-수정내역-2026-08-30.md)

> 대상: `marketing-team` v0.46.1
>
> 목적: 정적 검사가 대신할 수 없는 **실제 스킬 발화·담당 호출·파일 생성·실행 영수증 검증**을
> 초급·중급·고급 마케터 시나리오로 확인한다.

## 이번 검증의 완료 조건

아래 세 항목을 **설치본을 사용하는 Claude Code의 서로 다른 새 대화**에서 모두 확인해야 한다.

| 수준 | 반드시 확인할 것 |
|---|---|
| 초급 | 자연어 요청이 006으로 라우팅되고 샘플 리뷰 200건을 분석해 실제 파일을 남기는가 |
| 중급 | 046이 손익분기 ROAS·3안을 만들고 AI 사업검토자 **재무** 관점을 실제 호출하는가 |
| 고급 | 061 → 073 → 065 → 066 조합이 실행되고 AI 사업검토자 **경영** 관점을 실제 호출하는가 |

세 시나리오 모두 산출물, `run.json`, 원장 기록이 있어야 하며 실행 영수증 검사가 통과해야 한다.
화면에 답이 나왔더라도 파일이 없으면 실패다.

2026-08-30 런타임 보호 이후에는 G2 화면에 `[실행 계획]`과 `[승인 요청]`이 보여야 한다.
사용자가 정확히 `진행 승인`이라고 답하기 전 분석/생성용 Bash·Write·Edit·검토자 호출이 훅에서 거부되고,
`outputs/`나 `run.json`이 먼저 생기지 않아야 한다.
단, 정확한 계획을 만들기 위한 `rg`·`grep`·`ls` 같은 읽기 전용 조회는 허용된다.

## 1. 시작 전 준비

### Claude Code 상태

1. Claude Code에서 `/login`을 실행한다.
2. 플러그인 업데이트 후 Claude Code를 완전히 종료하고 다시 연다.
3. 터미널에서 아래 명령으로 인증·설치 버전·마켓플레이스 출처를 확인한다.

```bash
claude auth status
claude plugin list
claude plugin marketplace list
```

통과 기준:

- `loggedIn`이 `true`다.
- `marketing-team`이 `enabled`이며 버전이 `0.46.1` 이상이다.
- **개발 확인**에서는 `Source: Directory`를 쓸 수 있지만 릴리스 설치본 검증으로 세지 않는다.
- **릴리스 확인**에서는 태그를 푸시한 뒤 GitHub 마켓플레이스
  `steveaimkt/marketing-team@{태그}`에서 설치한다. `claude plugin marketplace list`의
  `marketing-team` 출처가 `GitHub`여야 한다.
- 설치된 마켓플레이스 플러그인은 Claude Code가 `~/.claude/plugins/cache`로 복사한다.
  스킬이 열릴 때 보이는 base 경로가 이 캐시 아래여야 하며 저장소의
  `100skills-team/plugins/marketing-team`이면 릴리스 설치본 검증이 아니다.

현재 `marketing-team`이 `Source: Directory`라면 그 설치는 개발 확인까지만 맡긴다. GitHub 태그로
바꾸는 작업은 기존 마켓플레이스를 제거하면서 설치 플러그인도 함께 지우므로, **태그가 원격에 올라간
뒤 별도 릴리스 단계에서** 진행한다.

### 깨끗한 작업 폴더

기존 `inputs/`, `outputs/`, `brand/`가 라우팅과 샘플 선택에 영향을 주지 않도록 수준별로 빈 폴더를
하나씩 준비한다. 세 시나리오를 같은 대화에서 연속 실행하지 않는다.

```text
claude-validation/
├── beginner/
├── intermediate/
└── advanced/
```

각 폴더로 실제 이동한 뒤 그 위치에서 `claude`를 실행해 **새 대화**로 시작한다. 저장소에서 연
대화에 「작업 폴더는 beginner」라고 덧붙이는 방식은 프로젝트의 `.claude/skills`가 먼저 열릴 수 있어
격리 검증이 아니다. 테스트 중 Claude가 선택을 물으면 아래에 적힌 응답을 사용자가 직접 보낸다.
질문을 건너뛰거나 대신 판단하지 않는지도 검증 대상이다.

## 2. 초급 마케터 시나리오

### 첫 요청

```text
뭘 해야 할지 모르겠는데 고객 리뷰부터 보면 좋을 것 같아
```

샘플 사용 여부를 물으면:

```text
A 브랜드 샘플 리뷰 200건으로 끝까지 진행해줘.
```

CS 전달 여부를 물으면:

```text
자동 전달하지 말고 CS 우선 확인 목록만 결과에 남겨줘.
```

계획 승인을 물으면:

```text
진행 승인
```

### 합격 기준

- 번호나 전문 명령어를 쓰지 않아도 **소비자 리뷰 분석(006)**으로 좁혀진다.
- `sample-data/A브랜드-리뷰-200건.csv`를 사용하고 결과에 `[샘플]`을 표시한다.
- CSV는 실제 쉼표 구분 데이터이며 Markdown 표를 `.csv`라는 이름으로 저장하지 않는다.
- 아래 두 산출물이 실제로 존재한다.
  - `006-review-mining.csv`
  - `006-review-mining-해설.md`
- 개인정보가 마스킹되고 TOP 5 페인포인트와 `CS 우선 확인` 목록이 나온다.
- 사용자 화면에 내부 용어 `에스컬레이션`이 나타나지 않는다.
- 검토가 필요 없는 분석이므로 AI 사업검토자나 AI 규제검토자를 억지로 호출하지 않는다.
- 같은 폴더의 `run.json`이 `status: completed`, `integrity.status: current`다.
- `logs/build-log.md`에 이번 실행 한 행이 추가된다.

### 즉시 실패로 보는 경우

- 006이 아닌 개인 스킬이나 다른 플러그인이 요청을 가로챈다.
- 리뷰 파일이 없다는 이유만으로 작업을 중단하고 샘플 폴백을 쓰지 않는다.
- 결과가 대화창에만 있고 파일이 없다.
- `.csv` 파일 안에 Markdown 제목·설명·표가 들어 있다.
- 실행하지 않은 담당 검토를 통과했다고 표시한다.

## 3. 중급 마케터 시나리오

### 첫 요청

```text
광고 성과를 손익분기로 판정하고 다음 주 예산 재배분안을 만들어줘.
데이터가 없으면 A 브랜드 샘플을 쓰고 보수·중립·공격 3안으로 비교해줘.
```

계획 승인을 물으면:

```text
진행 승인
```

3안 중 선택을 물으면:

```text
보수안을 추천안으로 두고 검토와 저장까지 마무리해줘.
```

### 합격 기준

- **ROAS 진단·예산 재배분(046)**이 열린다.
- 샘플 프로필의 공헌이익률 50%를 근거로 손익분기 ROAS를 `2.0`으로 계산한다.
- 보수·중립·공격 **정확히 3안**에 이동 금액, 예상 ROAS, 리스크가 들어간다.
- 제안을 실제 집행처럼 표현하거나 광고 계정을 변경하지 않는다.
- 기간이 없거나 다른 채널 자료를 합쳐 비교하지 않고 `[기간 미확인]`으로 제외한다.
- `046-roas-budget-rebalance.md`가 실제 파일로 남는다.
- `writes_to`에 없는 `046-roas-budget-rebalance.html` 같은 추가 파일을 만들지 않는다.
- AI 사업검토자 **재무** 관점을 실제 호출한다.
- 같은 폴더에 `review-재무.md`가 있고, 보고서가 정확한 산출물 경로를 적는다.
- 검토가 조건부·반려였다면 AI 마케터가 수정한 뒤 **같은 현재 파일을 다시 검토**한다.
- `run.json`의 `skills`에 `046`이 있고 재무 검토의 산출물·보고서 SHA-256이 현재 파일과 일치한다.
- 최종 상태가 `status: completed`, `integrity.status: current`이며 원장 한 행이 존재한다.

### 즉시 실패로 보는 경우

- BEP 없이 ROAS가 높고 낮음만 비교한다.
- 시나리오가 하나뿐이거나 총예산이 근거 없이 달라진다.
- AI 사업검토자를 부르지 않고 AI 마케터가 자체 판정한 뒤 `✅`로 끝낸다.
- `review-재무.md`가 없거나 다른 산출물을 검토했다.
- 검토 후 본문을 수정하고도 다시 검토하지 않는다.
- Claude가 실제 광고 예산을 옮겼다고 주장한다.

## 4. 고급 마케터 시나리오

### 첫 요청

```text
샘플 매출·퍼널·고객마스터를 결합해서 매출 병목, 우선 공략 세그먼트,
고객 여정 이탈점, KPI 트리를 한 번에 정리해줘.
061 → 073 → 065 → 066 순서의 즉석 조합으로 진행하고,
파일별 기간이 다르면 공통 기간만 직접 비교해줘.
우선순위는 AI 사업검토자 경영 관점 검토까지 받아줘.
```

> ⚠️ **`073 → 065` 순서는 일부러 거꾸로 준 것이다.** 정방향은 `065 → 073`이다 —
> `065`의 `chains_to`가 `["073","074"]`이고 `073`의 `inputs`에 `065 세그먼트 리포트(선택)`가 있다.
> 그리고 `073` 계약 5는 **「065가 있으면 세그먼트 기준으로 그린다 · 평균 고객 1장으로 뭉개지 않는다」**이다.
> 이 순서로는 073이 065를 받을 수 없으므로 **반드시 「평균 고객 1장」이 된다.**
>
> **시험하는 것은 그 결과가 아니라 시스템이 알아채는가다.** 실사용의 즉석 조합은 원래 비정규
> 순서로 들어온다. 조용히 그리면 실패, 스스로 밝히면 통과다. 순서를 고쳐 주지 않는다.

계획 승인을 물으면:

```text
진행 승인
```

중간 선택을 물으면:

```text
데이터 근거가 가장 큰 세그먼트와 이탈점 하나를 우선안으로 선택하고 끝까지 진행해줘.
근거가 없는 값은 추정하거나 숨기지 말고 [자료 없음] 또는 [측정 필요]로 표시해줘.
```

### 합격 기준

- `run.json`의 `skills`가 `061`, `073`, `065`, `066` 순서로 기록된다.
- 앞 단계 산출물 경로가 다음 단계 입력으로 이어지고, 중간 단계를 말없이 생략하지 않는다.
- 판매 분석, 고객 여정, RFM, KPI 트리의 필수 산출물이 실제 파일로 남는다.
- 여러 스킬 조합 결과가 런타임 규칙에 따라 **주 스킬의 산출물 폴더**에 모인다.
- 입력 기간표를 먼저 만들고 다음 기간 차이를 구분한다.
  - 매출: 2026-06-01~2026-06-30
  - 퍼널: 2026-05-01~2026-07-29
  - 고객마스터: 2025-07-02~2026-06-30
- 직접 비교와 비율 계산에는 공통 기간인 `2026-06-01~2026-06-30`만 사용한다.
- 더 긴 기간은 추세 참고로만 쓴다. 세 샘플의 6월 합계가 다르므로 `[자료 충돌]`을 밝히고
  파일 사이의 합산·나눗셈은 하지 않는다.
- 고객 데이터는 개인정보를 새 결합 키로 만들지 않는다.
- 고객마스터 3,506행·고객 880명을 통째로 화면에 펼치지 않고 집계하며 식별자를 마스킹한다.
- CSV·해설·마스킹 설명·예시·검토 보고서 어디에도 원문 고객ID가 한 번도 나오지 않는다.
- 고객 대체키는 실행별 임의값이며 무염 SHA-256 앞자리처럼 원문 후보로 되찾을 수 있는 값이 아니다.
- KPI 트리는 북극성 지표 1개, 계산식·소스·주기·현재값, 경고/위험 임계값을 갖는다.
- 결과에 `우선순위·무엇부터`가 있으므로 AI 사업검토자 **경영** 관점을 실제 호출한다.
- `review-경영.md`가 있으며 검토 대상 경로와 현재 산출물 SHA-256이 일치한다.
- 모든 필수 산출물의 검토 누락이 없고 `run.json`이 `completed/current`다.
- **073이 065를 받지 못했음을 스스로 밝히고**, 그 여정이 계약이 금지한 「평균 고객 1장」임을
  산출물에 적으며, 다음 액션에 073 재실행을 넣는다. (순서가 거꾸로인 것은 의도된 함정이다)
- `run.json`에 `pii` 블록이 있고 개인정보 검사가 통과한다 (065는 `pii: true`다).
- `logs/build-log.md`에 이번 조합 실행을 찾을 수 있다.

### 즉시 실패로 보는 경우

- 4개 중 일부만 실행하고 사용자에게 알리지 않는다.
- 서로 다른 전체 기간의 숫자를 같은 분모처럼 직접 비교한다.
- 고객 이름·이메일을 결합 키로 새로 사용하거나, 설명·예시·검토 보고서에 원문 식별자를 노출한다.
- 서로 맞지 않는 세 샘플을 공통 기간이라는 이유만으로 교차 계산한다.
- KPI 트리 말단이 매출 같은 결과 지표로 끝나고 팀이 움직일 입력 지표가 없다.
- 우선순위를 만들고도 경영 관점 검토를 호출하지 않는다.
- 다중 산출물 중 일부만 검토한 영수증을 완료 처리한다.
- 073이 065 없이 여정을 그리고도 **그 사실을 말하지 않는다.**
- `pii: true` 스킬을 돌리면서 `run.json`에 `pii` 블록을 넣지 않는다 (검사가 조용히 건너뛴다).

## 5. 각 시나리오가 끝난 뒤 공통 검사

Claude Code 대화에 아래처럼 요청한다.

```text
방금 실행의 산출물, 검토 보고서, run.json, logs/build-log.md가 실제로 존재하는지 확인해줘.
그다음 플러그인의 run-receipt.mjs verify로 run.json을 검사하고,
검사 결과와 run.json 경로만 알려줘. 파일은 수정하지 마.
```

통과 기준:

- 검증 명령이 성공 종료한다.
- `run.json`의 `status`는 `completed`다.
- `integrity.status`는 `current`다.
- 입력·프로필·스킬·산출물·검토 보고서 해시가 현재 파일과 맞는다.
- `required_reviews`에 지정한 산출물마다 대응하는 최종 검토가 있다.
- 원장에는 산출물 경로나 `run_id`가 실제로 들어 있다.
- `pii` 블록이 있는 실행이면 **개인정보 검사가 함께 통과한다** — 원문 식별자 인용 0 ·
  대체키 복원 0 · 원문↔대체키 대응표 0. (`finalize`·`verify`가 자동으로 돌린다)

### ⛔ 결과를 기록하기 **직전에 `verify`를 한 번 더** 돌린다

실측 2026-08-30 — 검증이 끝나고 10분 만에 저장소가 수정돼 **검증한 빌드가 즉시 교체됐다.**
그때 `verify`를 다시 돌렸으면 `🟡 실행 뒤 바뀐 스킬`로 바로 잡혔다.

```bash
node "플러그인경로/scripts/run-receipt.mjs" verify outputs/.../run.json
```

`🟡 실행 뒤 바뀐 스킬·입력·프로필`이 하나라도 뜨면 **그 결과는 이미 없는 빌드의 것이다.**
기록에 ✅를 쓰지 말고 새 빌드로 재실행한다.

실패 시에는 산출물을 조용히 고쳐 통과시키지 않는다. 먼저 실패 원인과 경로를 기록하고, 수정이 필요하면
수정 → 담당 재검토 → `review` 재봉인 → `finalize` → `verify` 순서로 다시 확인한다.

## 7. 최종 판정 원칙

- 밟지 않은 항목은 `⬜ 미실행`이다. 추정으로 `✅`를 쓰지 않는다.
- 담당을 호출하지 못한 폴백 결과는 최대 `⚠️`다.
- 대화 응답이 좋아도 파일이나 영수증이 없으면 `❌`다.
- `verify` 실패 상태에서 G4가 완료를 선언했으면 `❌`다.
- `running`·`pending` 영수증에서 `verify`가 exit 0이면 `❌`다.
- 계획 승인 전에 쓰기·분석/생성용 셸 실행·검토자 호출이 하나라도 실행되면 `❌`다.
- 세 시나리오가 모두 설치본에서 통과하기 전에는 **릴리스 실기동 통과**로 보지 않는다.
- 문제를 고쳤다면 최초 실패, 수정 내용, 같은 문장으로 재검증한 결과를 모두 기록한다.

전체 릴리스 체크리스트는 저장소 루트 기준
`plugins/marketing-team/scripts/실제확인.md`, 실행 영수증 규격은
`plugins/marketing-team/docs/실행-영수증.md`를 정본으로 삼는다.
