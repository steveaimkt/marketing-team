> 후속 계획: [오케스트레이터 개선 플랜](./오케스트레이터-개선-플랜.md)

| 구분 | 상태 | 근거 |

| 자동 회귀 | ✅ 통과 | 100개 스킬·훅·영수증·PII·패키지 검사 오류 0 |

**결론:** 코드와 자동 검사는 통과했다. 다만 수정본을 설치한 새 대화 3개에서 끝까지 완주하기 전에는
릴리스 최종 통과로 판정하지 않는다.

## 2. 수정 전 실제 확인 결과

Claude Code의 서로 다른 빈 작업 폴더에서 자연어 요청으로 확인했다.

| 수준 | 실제 동작 | 판정 |
|---|---|---|
| 초급 | 006으로 라우팅 · CSV 201행 · `completed/current` | ⚠️ TOP 5 계약인데 페인포인트 군집이 4개 |
| 중급 | 046으로 라우팅했지만 G2 승인 전에 `run.json`·MD·계획 밖 HTML 생성 · 재무 검토 미호출 · `running/pending`인데 `verify` exit 0 | ❌ |
| 고급 | 4개 스킬을 찾았지만 순서를 `061→065→073→066`으로 변경 · 승인 전 파일 작성 · 영수증·검토·최종 응답 없이 장시간 실행 | ❌ |

핵심 원인은 좋은 문장을 더 쓰는 문제가 아니었다. 승인·상태·경로·산출물 범위가 프롬프트에만 있고
런타임에서 강제되지 않아, 모델이 절차를 건너뛰어도 실행할 수 있었다.

## 3. 적용한 수정

### FIX-01 · 미완료 영수증의 거짓 통과 차단

**문제**

- `run.json`이 `running`, `integrity: pending`이어도 현재 파일에 문제가 없으면 `verify`가 exit 0이었다.
- 실제 완료와 “현재까지 파일이 존재함”을 구분하지 못했다.

**수정**

- `verify`는 아래 조건을 모두 만족할 때만 성공한다.
  - `status: completed`
  - `integrity.status: current`
  - `completed_at` 존재
- 검사 기준도 항상 완료 상태로 고정해 필수 산출물·검토·원장을 전부 확인한다.

**수정 파일:** `scripts/run-receipt.mjs`, `scripts/test-run-receipt.mjs`

### FIX-02 · G2 승인선을 PreToolUse 훅으로 강제

**문제**

- “계획을 보여주고 기다린다”는 문서 규칙만 있었고 기술적 차단은 없었다.
- 승인 전에 분석·파일 생성·검토자 호출이 가능했다.

**수정**

- G2 화면을 `[실행 계획]`으로 시작하고 `[승인 요청]`으로 끝낸다.
- 사용자는 정확히 `진행 승인`이라고 답한다.
- 승인 전 다음 동작을 차단한다.
  - `Write`, `Edit`, `NotebookEdit`
  - 분석·생성용 `Bash`
  - `Agent`, `Task`
  - 계획에 없는 `Skill`
- 정확한 계획을 만들기 위한 `rg`, `grep`, `ls`, `find`, `head`, `wc` 등의 읽기 전용 조회만 허용한다.
- 변수 선언으로 경로를 재사용하는 읽기 명령은 허용하되, 명령 치환·리다이렉션 쓰기는 차단한다.
- AI 마케터가 열리지 않은 일반 Claude Code 세션에는 개입하지 않는다.

**수정 파일:** `hooks/hooks.json`, `scripts/runtime-guard.mjs`, `scripts/test-runtime-guard.mjs`,
`skills/AI-마케터/SKILL.md`

### FIX-03 · 계획 밖 도구와 산출물 추가 차단

**문제**

- 중급 실행이 요청하지 않은 시각화 스킬을 호출하고 HTML을 추가 생성했다.
- 실행 범위와 시간·검토 대상이 조용히 늘어났다.

**수정**

- 계획에 이름이 없는 추가 Skill 호출을 훅에서 차단한다.
- 한 실행의 허용 산출물을 선택 스킬들의 `writes_to` 합집합으로 제한한다.
- 단일 스킬은 `writes_to` 경로를 그대로 사용한다.
- 여러 스킬 조합은 선언된 파일명을 유지하면서 마지막 주 스킬 폴더에 모은다.
- 다른 형식이 필요하면 기존 실행에 끼워 넣지 않고 별도 계획·승인·영수증으로 분리한다.

**수정 파일:** `scripts/run-receipt.mjs`, `skills/AI-마케터/SKILL.md`, `docs/공통규약.md`

### FIX-04 · 고급 조합 순서 변경 차단

**문제**

- 사용자가 지정한 `061→073→065→066`을 모델이 `061→065→073→066`으로 바꿨다.

**수정**

- 네 스킬이 함께 선택된 실행은 `run-receipt start`에서 지정 순서를 기계 검사한다.
- 순서가 다르면 산출물 생성 전에 시작을 실패시킨다.

**수정 파일:** `scripts/run-receipt.mjs`, `scripts/test-run-receipt.mjs`

### FIX-05 · 플러그인 실행 루트 단일화

**문제**

- 현재 소스를 `--plugin-dir`로 열었는데도 실행 중 다른 캐시 설치본을 탐색할 수 있었다.
- 저장소와 설치본이 섞이면 검증한 코드와 실제 사용 코드가 달라진다.

**수정**

- Claude Code 플러그인 실행 중에는 `${CLAUDE_PLUGIN_ROOT}` 한 곳만 사용한다.
- 홈·루트 전체 `find`와 현재 루트가 아닌 다른 `~/.claude/plugins/cache` 참조를 차단한다.
- 환경 변수가 없는 직접 폴더 실행에서만 현재 폴더를 패키지 루트로 사용한다.

**수정 파일:** `scripts/runtime-guard.mjs`, `docs/공통규약.md`

### FIX-06 · PII 검사 블록 유실과 미선언 차단

**문제**

- `pii: true` 스킬이 초안에 `pii` 블록을 넣어도 `start`가 최종 영수증에 보존하지 않았다.
- 결과적으로 `finalize`와 `verify`의 개인정보 검사가 조용히 건너뛸 수 있었다.

**수정**

- `pii: true` 스킬은 `run.json` 초안의 `pii` 블록을 필수로 한다.
- `pii.source`가 동일 실행의 `inputs`에 없으면 시작을 거부한다.
- `id_columns`를 필수로 검사하고 정규화한 `pii` 블록을 최종 영수증에 보존한다.
- 산출물과 검토 보고서의 원문 식별자·복원 가능한 대체키·대응표를 완료 시 검사한다.

**수정 파일:** `scripts/run-receipt.mjs`, `scripts/pii-check.mjs`, 관련 테스트

### FIX-07 · 검증 문서와 실제 명령 통일

**수정**

- 세 시나리오의 G2 승인 응답을 `진행 승인`으로 통일했다.
- 승인 전 정지·추가 HTML 금지·미완료 `verify` 실패를 합격 기준에 추가했다.
- 저장소 기준 기록 경로를 `plugins/marketing-team/scripts/실제확인-기록/`으로 명시했다.
- 자동 테스트 결과와 실기 결과를 구분해 기록하도록 했다.

**수정 파일:** `docs/클로드코드-실기검증.md`, `scripts/실제확인.md`,
`scripts/실제확인-기록/f964c6d.md`, `docs/실행-영수증.md`

## 5. 실제 Claude Code 확인

현재 소스를 `--plugin-dir`로 고정한 빈 임시 폴더에서 자연어 요청을 보냈다.

확인된 동작:

- 자연어 요청이 ROAS 진단·예산 재배분(046)으로 라우팅됐다.
- 손익분기 ROAS 2.0, `writes_to` 정본 `.md`, 재무 관점 검토가 계획에 표시됐다.
- `[실행 계획]`과 `[승인 요청]`을 출력한 뒤 멈췄다.
- 승인 전 임시 폴더에 생성된 파일은 0개였다.
- 읽기 전용 조회의 변수 선언 처리 보완은 마지막 자동 회귀에서 통과했다.

이 확인은 **승인 전 정지 확인**이다. `진행 승인` 뒤 산출물·검토·영수증 완료까지의 전체 실기는
아래 잔여 작업으로 남아 있다.

## 6. 사용 시 달라지는 점

1. AI 마케터가 계획을 보여준다.
2. 사용자는 계획을 확인한 뒤 `진행 승인`이라고 답한다.
3. 그 전에는 파일이나 분석 결과가 만들어지지 않는다.
4. 계획을 바꾸면 새 `[실행 계획]`과 새 승인이 필요하다.
5. 다른 출력 형식이 필요하면 현재 실행에 임의로 추가하지 않고 별도 실행으로 분리한다.
6. `verify`의 ✅는 이제 실제 `completed/current` 완료를 뜻한다.

## 8. 릴리스 판정 원칙

- 자동 검사가 초록이어도 새 대화 실기를 밟지 않았으면 `⬜ 미실행`이다.
- `running`, `pending`, `verification-failed`에서 완료를 선언하면 실패다.
- 담당 검토를 호출하지 못한 결과는 최대 `⚠️`다.
- GitHub 태그 설치본이 아닌 `Source: Directory` 결과는 개발 확인으로만 센다.
- 초급·중급·고급 완주와 설치본 검증이 끝난 뒤에만 릴리스 통과로 바꾼다.
