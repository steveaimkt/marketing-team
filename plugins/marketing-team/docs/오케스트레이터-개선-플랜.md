# 마케팅팀 오케스트레이터 개선 플랜

> 작성일: 2026-08-30
> 대상: `marketing-team` v0.46.1 이후
> 관련 문서: [런타임 안정성 수정 내역](./런타임-안정성-수정내역-2026-08-30.md)
> 목표: AI 마케터의 판단력은 유지하면서 라우팅·승인·체인·검토·완료를 재현 가능한 실행 시스템으로 만든다.

## 1. 한 줄 결론

현재 구조는 **상태와 계약으로 실행을 통제하는 오케스트레이터**까지 올라왔다.
P0인 계획 봉인·체인 그래프·단계 재개는 구현됐고, 남은 핵심은 설치본 새 대화 실기와
실측 기반 하드 예산·반복 오류 회로 차단이다.

```text
구현 상태  P0 완료 · P1 부분 완료 · 릴리스 실기 미완
기계 검증  verify 오류 0 · plugin validate 통과
남은 관문  현재 터미널 Claude 재로그인 후 초급/중급/고급을 서로 다른 설치본 새 대화에서 완주
```

새 실행 담당이나 가상의 조직은 추가하지 않는다.

```text
사용자
  ↓
AI 마케터                    판단·제작·보고
  ↓
오케스트레이션 제어층         라우팅·계획 봉인·상태 전이·예산·복구
  ├─ AI 사업검토자            사업 판단
  └─ AI 규제검토자            규제·개인정보 판단
```

스킬 100번 `나만의 마케팅 에이전트 구축`은 사용자의 업무 배선 설계다.
이 문서가 개선하는 것은 그와 다른 **플러그인 내부 런타임 제어층**이다.

## 2. 현재 구조 진단

### 잘되어 있는 것

- `ROUTING.md` 한 장만 상시 읽고 선택된 스킬만 여는 Progressive Disclosure 구조
- G1~G5로 사용자 결재 지점을 단순화한 대화 흐름
- `review`, `gate`, `pii`, `writes_to`가 스킬 frontmatter에 선언됨
- AI 마케터와 독립 검토 담당의 제작·판정 권한 분리
- `run.json`과 SHA-256으로 입력·산출물·검토 보고서의 동일성 확인
- PreToolUse 훅으로 G2 승인 전 쓰기·실행 차단
- 샘플·추정·자료 충돌·기간 불일치에 대한 안전 규칙

### 남은 구조적 한계

| 영역 | 현재 | 위험 |
|---|---|---|
| 라우팅 | AI 의미 판단 + 로컬 후보 라우터 + 596건 회귀 | 새 복합 표현의 분해·동률 질문은 설치본 실기가 더 필요 |
| 계획 | `plan/v1` 해시와 승인 봉인 | G2를 구조화 계획에서 렌더링하는 실제 대화 준수 여부 |
| 체인 | 정본 15개와 입력 의존 DAG 기계 검사 | 이름 없는 즉석 체인의 업무적 타당성은 여전히 AI 판단 |
| 실행 상태 | 단계별 상태·입력 지문·선택적 재개 | 화면 예상 남은 시간은 없음 |
| 실행 예산 | 시간·검토 자동 계측, 도구 호출 수동 계측·소프트 경고 | 자동 호출 계측과 실측 기반 하드 상한 없음 |
| 검토 | frontmatter에서 산출물별 요구 자동 생성 | 외부 검토 담당의 실제 호출은 설치 환경에 좌우됨 |
| 복구 | 변경 영향을 받은 단계만 무효화하고 재개 | 프로세스 강제 종료 직전 이벤트 유실 가능 |
| 관측 | 원장 + `orchestrator-events.jsonl` + 요약 명령 | 장기 집계·대시보드 없음 |
| 테스트 | 라우팅·계획·체인·단계·검토·PII·이벤트 회귀 | 설치본 새 대화 3종과 실제 사용자 표본 미완 |

### 일반 마케터 기준 최우선 개선 5가지

일반 사용자는 스킬 번호·frontmatter·영수증·훅을 몰라도 된다. 아래 다섯 가지가 화면 밖에서
정상 작동해야 “하고 싶은 일을 말하면 결과가 나오는 플러그인”이 된다.

| 우선순위 | 개선 과제 | 일반 마케터에게 중요한 이유 | 완료 기준 | 연결 Phase |
|---|---|---|---|---|
| **1** | **자연어 라우팅 정확도** | 사용자는 006·046 같은 번호를 모른다. 평소 말로 요청해도 정확한 업무가 선택돼야 한다. | 주요 요청 Top-1 95% 이상 · Top-2 99% 이상 · 애매할 때 질문 1회 | Phase 0·2 |
| **2** | **계획·승인·실행 일치** | 승인한 계획과 실제 스킬·순서·산출물이 다르면 결과를 신뢰할 수 없다. | 계획 해시 봉인 · 변경 시 재승인 · 승인 전 실행 0건 | Phase 1 |
| **3** | **결과물 완주와 중단 복구** | 좋은 대화보다 파일이 실제로 남고 다음 날 다시 열리는 것이 중요하다. | 파일·검토·원장·영수증 생성 · 중단 지점부터 재개 · 완료 오표기 0건 | Phase 3 |
| **4** | **데이터 입력 경험과 안전성** | CSV 위치·기간·열 이름을 모르면 첫 사용에서 막힌다. 샘플 오인과 개인정보 유출도 위험하다. | 채널별 가져오기 안내 · 입력 자동 탐색 · 샘플 표시 · 기간 충돌·PII 자동 차단 | Phase 1·4 |
| **5** | **실행 속도와 설치본 일관성** | 오래 멈추거나 개발본·캐시본이 다르면 사용자는 플러그인이 고장 났다고 판단한다. | 진행 상태·실행 예산·안전 중단 · GitHub 설치본 회귀 통과 | Phase 0·4·5·6 |

사용자 가치 기준 실행 순서:

```text
자연어 라우팅 기준선
 → 계획 스키마·승인 해시·상태 머신
 → 단계별 완주·중단 복구
 → 데이터 가져오기·개인정보 안전
 → 실행 예산·설치 및 업데이트 검증
```

스킬을 더 추가하는 것보다 이 다섯 가지를 먼저 개선한다. 현재 플러그인의 가장 큰 위험은
기능 부족이 아니라 **요청부터 완료까지의 연결이 모델 판단에 많이 의존한다는 것**이다.

## 3. 목표 원칙

1. **판단은 AI, 전이는 기계** — 무엇을 할지는 AI가 제안하지만 다음 상태로 갈 수 있는지는 코드가 결정한다.
2. **계획과 실행의 동일성** — 승인받은 스킬·순서·입력·산출물·검토 정책만 실행한다.
3. **작은 명령과 점진적 공개** — 거대한 프롬프트 한 번 대신 라우팅·계획·실행·검증을 작은 단계로 나눈다.
4. **중간 산출물도 계약** — 체인의 앞 단계 출력이 다음 단계 입력으로 실제 연결됐는지 기록한다.
5. **실패를 정상 상태로 취급** — 막힘·중단·예산 초과를 숨기지 않고 재개 가능한 상태로 남긴다.
6. **설치본 한 곳** — 실행 중 패키지 루트는 `${CLAUDE_PLUGIN_ROOT}` 하나다.
7. **기본은 보수적** — 승인·검토·PII가 불확실하면 통과가 아니라 정지다.
8. **기존 사용자 경험 유지** — 사용자는 계속 AI 마케터 한 명과 대화한다.

## 4. 목표 상태 머신

```text
INTAKE
  ↓
ROUTED
  ↓
PLAN_READY
  ↓
AWAITING_APPROVAL ── 사용자 수정 ──→ PLAN_READY
  ↓ 진행 승인
APPROVED
  ↓
RUNNING(step 1..n)
  ├─ 예산 초과/자료 부족 ──→ BLOCKED
  ├─ 도구 오류 ───────────→ INTERRUPTED
  └─ 단계 완료 ───────────→ REVIEWING 또는 다음 step
                               ↓
                            FINALIZING
                               ↓
                            COMPLETED
```

허용 전이는 코드로 고정한다.

| 현재 상태 | 허용되는 다음 상태 | 금지 예시 |
|---|---|---|
| `draft` | `routed` | 산출물 작성 |
| `routed` | `plan-ready` | 검토자 호출 |
| `plan-ready` | `awaiting-approval` | 분석 실행 |
| `awaiting-approval` | `approved`, `plan-ready` | 사용자 승인 없는 `running` |
| `approved` | `running` | 계획에 없는 스킬 추가 |
| `running` | `reviewing`, `blocked`, `interrupted` | 산출물 없이 `completed` |
| `reviewing` | `running`, `finalizing`, `blocked` | 조건부 판정으로 완료 |
| `finalizing` | `completed`, `verification-failed` | 원장·해시 누락 통과 |

## 5. 목표 구성 요소

### A. 라우터 · `scripts/router.mjs`

역할은 **후보를 좁히는 것까지**다. 산출물을 만들지 않는다.

입력:

- 사용자 요청
- 작업 폴더 신호 (`brand/`, `inputs/`, 최근 원장)
- `ROUTING.md` 또는 생성된 라우팅 색인

출력 예시:

```json
{
  "request_class": "analysis-and-decision",
  "candidates": [
    { "id": "046", "score": 0.91, "reason": "ROAS 판정과 예산 재배분" },
    { "id": "045", "score": 0.42, "reason": "주간 성과 취합 표현" }
  ],
  "decision": "046",
  "confidence": "high",
  "needs_user_choice": false
}
```

규칙:

- 점수가 낮거나 상위 두 후보 차이가 작으면 한 번 묻는다.
- 복합 요청은 먼저 하위 업무로 분해한 뒤 최대 4개만 제안한다.
- `chains_to`는 후보 근거이지 자동 실행 명령이 아니다.
- 라우터 평가셋은 각 스킬의 `routing-eval.jsonl`을 통합해 만든다.

### B. 계획 컴파일러 · `scripts/plan-compiler.mjs`

AI가 쓴 G2 계획을 기계가 검사할 수 있는 구조로 변환한다.

```json
{
  "schema": "marketing-team.plan/v1",
  "plan_id": "...",
  "request": "...",
  "skills": ["046"],
  "steps": [
    {
      "step": 1,
      "skill": "046",
      "inputs": ["plugin:sample-data/A브랜드-채널성과-90일.csv"],
      "outputs": ["workspace:outputs/.../046-roas-budget-rebalance.md"],
      "reviews": [{ "kind": "business", "perspective": "재무" }]
    }
  ],
  "budget": { "tool_calls": 0, "wall_minutes": 0, "review_rounds": 3 },
  "plan_sha256": "..."
}
```

검사 항목:

- 스킬이 실제 존재하는가
- 순서가 `requires`, `inputs`, `chains_to`와 충돌하지 않는가
- 모든 `writes_to`가 예정 산출물에 있는가
- `review`, `gate`, `pii` 정책이 빠지지 않았는가
- 조합의 앞 출력이 뒤 입력으로 연결되는가
- 승인 화면의 경로와 구조화 계획의 경로가 같은가

### C. 승인 봉인 · 계획 해시

현재의 `진행 승인` 문장은 유지하되 승인 대상을 명확히 한다.

1. 계획 컴파일러가 `plan_sha256`을 만든다.
2. G2 화면은 해당 계획에서 렌더링한다.
3. 사용자가 `진행 승인`이라고 답하면 현재 `plan_sha256`을 승인 상태로 봉인한다.
4. 이후 스킬·순서·출력·검토가 달라지면 새 계획과 새 승인이 필요하다.

훅은 단순히 최근 문장을 찾는 수준에서 다음 단계로 발전한다.

- 현재 계획 ID 존재
- 승인된 계획 해시와 현재 계획 해시 일치
- 호출하려는 도구가 해당 단계에서 허용됨
- 쓰려는 파일이 현재 단계의 outputs 또는 허용된 보고서 경로임

### D. 체인 컴파일러 · `scripts/chain-compiler.mjs`

특정 시나리오의 번호를 코드에 하드코딩하지 않는다.

스킬 frontmatter에서 실행 그래프를 만든다.

```text
requires + inputs + chains_to + writes_to + review + gate + pii
                              ↓
                        실행 DAG
```

검사:

- 순환 체인
- 앞 단계 없이 실행할 수 없는 입력
- 서로 다른 폴더·형식으로 끊긴 전달 경로
- 정본 체인과 사용자 지정 순서의 충돌
- 같은 파일을 두 단계가 덮어쓰는 충돌

사용자가 역방향 순서를 명시하면 자동 교정하지 않는다.
G2에서 충돌과 결과 제한을 설명하고, 승인받은 순서를 그대로 기록한다.

### E. 단계별 실행 영수증 · `run/v2`

기존 `run/v1`을 즉시 폐기하지 않고 `run/v2`를 추가한다.

```json
{
  "schema": "marketing-team.run/v2",
  "plan_id": "...",
  "plan_sha256": "...",
  "status": "running",
  "current_step": 2,
  "steps": [
    { "skill": "061", "status": "completed", "outputs": [], "verified_at": "..." },
    { "skill": "073", "status": "running", "inputs_from": [1] },
    { "skill": "065", "status": "pending" },
    { "skill": "066", "status": "pending" }
  ]
}
```

효과:

- 중단 지점을 정확히 알 수 있다.
- 완료된 단계를 다시 만들지 않고 다음 단계부터 재개한다.
- 앞 단계 산출물이 바뀌면 영향을 받는 뒤 단계만 무효화한다.
- 검토가 필요한 파일과 현재 해시를 단계별로 연결한다.

### F. 실행 예산과 회로 차단기

모든 실행에 예산을 둔다.

| 예산 | 초기 정책 | 초과 시 |
|---|---|---|
| 도구 호출 | 실측 P95를 수집한 뒤 스킬·체인별 상한 확정 | 새 도구 호출 차단 · 현재까지 결과 저장 |
| 벽시계 시간 | 단일/체인별 실측 P95 + 안전 여유 | `blocked: budget-exceeded` |
| 검토 라운드 | 최대 3회 | 사용자 판단 요청 |
| 동일 오류 | 2회 | 다른 방법 1회 또는 중단 |
| 계획 밖 스킬 | 0회 | 즉시 차단 · 새 계획 요구 |

처음부터 임의의 숫자로 전체를 막지 않는다.

1. 006·046·고급 조합의 정상 완주 도구 호출·시간을 기록한다.
2. 스킬 난이도별 P50/P95를 구한다.
3. 소프트 경고를 먼저 적용한다.
4. 두 번의 릴리스 실측 뒤 하드 상한을 켠다.

### G. 검토 정책 컴파일러 · `scripts/review-policy.mjs`

스킬의 선언을 실행 전 필수 검토표로 변환한다.

| 선언 | 자동 정책 |
|---|---|
| `review: 재무` | 모든 의사결정 산출물에 재무 검토 1건 |
| `gate: true` | 모든 대외 발행 산출물에 규제 검토 1건 |
| `pii: true` | 기계 PII 검사 + 규제검토자 개인정보 관점 |
| 여러 산출물 | 산출물별 검토 대상과 해시 명시 |

검토 결과가 `conditional`, `needs-fix`면 자동 완료하지 않는다.

```text
검토 → 수정 → 같은 현재 파일 재검토 → 최종 승인 봉인
```

| 회귀 | 해시 재현·민감도 7 · 계약 검사 4 · 지정 순서 2 · 승인 상태 5 · start 차단·통과 2 · 훅 계획 해시 5 |
| 훅 | `runtime-guard` 가 `plan.json` 을 함께 본다 · 승인 대기 ⛔ · 봉인 ✅ · 승인 뒤 변경 ⛔ · 재승인 ✅ · 계획 없음 ✅(하위 호환) |
| 지정 순서 | `requested_order` 를 계획 스키마와 해시에 넣었다. 사용자가 말한 순서를 모델이 바꾸면 컴파일이 막는다 (하드코딩 4스킬 검사의 일반화) |

**함께 앞당겨 끝난 것 (Phase 2~5)**

`review:`·`gate:` 선언은 `start`가 산출물별 `required_reviews`로 자동 생성한다.
그 전에는 검토 의무 60개 중 `pii` 8개만 강제되고 **52개가 「AI 마케터가 기억하기」**에 달려 있었다.
`scripts/output-checks.mjs` (`pii`·`csv-format`·`house-style`) 와
`scripts/check-flag-counts.mjs` 도 `verify.mjs` 에 물렸다. 추가로 자연어 후보 라우터,
15개 정본 체인 컴파일러, 단계 재개, 소프트 예산 사용량, JSONL 이벤트 요약을 회귀 검사에 연결했다.

## 12. 실제 마케터 실효성 평가

### 평가 결론

현재 플러그인의 **설계 실효성은 높고, 현장 실효성은 아직 검증 중**이다.

```text
절차·업무 범위·안전장치        강함
중급 마케터의 반복 업무 지원    실효성 높음
초보자의 설치 즉시 사용         보완 필요
복합 체인의 안정적 완주          보완 필요
실제 매출·ROAS 개선 효과         아직 증거 없음
```

현재 소스와 제한된 Claude Code 실기를 기준으로 한 **잠정 제품 실효성 점수는 83/100**이다.
이 숫자는 사용자 만족도나 매출 효과가 아니다. 일반 마케터가 업무를 시작해 재사용 가능한 결과까지
도달할 가능성을 평가한 설계 점수다.

### 일반 마케터가 체감할 강점

1. **무엇을 해야 하는지 모를 때 출발점을 준다.** 스킬 번호 대신 자연어와 동사형 선택지를 쓴다.
2. **결과가 파일로 남는다.** 대화가 끝나도 다음 주에 다시 열고 이어갈 수 있다.
3. **숫자에 판정을 붙인다.** ROAS·마진·기간·표본을 근거 없이 “좋다”라고 말하지 않는다.
4. **회사 데이터가 없어도 볼 수 있다.** 샘플로 먼저 결과를 보여 주고 실제 데이터 전환 경로를 안내한다.
5. **발행·예산·개인정보를 조심한다.** 일반 생성형 AI보다 업무 사고를 막는 구조가 강하다.

### 일반 마케터가 체감할 마찰

1. **첫 설정이 아직 폴더 중심이다.** `brand/`, `inputs/`, `outputs/`, `logs/` 개념을 알아야 한다.
2. **데이터를 직접 내려받아야 한다.** 데이터 사용 스킬은 대부분 플랫폼 내보내기에 의존한다.
3. **승인 단계가 반복처럼 느껴질 수 있다.** G1·G2를 왜 나누는지 화면 문장이 충분히 짧아야 한다.
4. **복합 실행은 오래 걸릴 수 있다.** 단계·재개 지점은 남지만 화면의 예상 남은 시간은 아직 없다.
5. **문서 숫자가 표류할 수 있다.** `데이터-가져오기.md`의 샘플 폴백 수는 48로,
   현재 생성 통계 52와 다르다. 사용자에게 보이는 숫자도 자동 검사 대상으로 넓혀야 한다.

### 실제 효과를 입증하는 사용자 검증

실제 마케터에게 유용하다고 확정하려면 기능 테스트가 아니라 **비교 사용성 테스트**가 필요하다.

권장 표본:

- 초급 5명
- 중급 5명
- 고급 5명
- 총 15명 · 각 5개 업무

비교 방식:

```text
같은 마케팅 요청
  A  일반 Claude
  B  marketing-team 플러그인

비교: 정확도 · 완료 시간 · 수정 횟수 · 파일 재사용성 · 의사결정 도움 · 신뢰도
```

핵심 측정 지표:

| 첫 업무 시작 성공률 | 90% 이상 |

### 최종 판단

이 플러그인의 가장 큰 가치는 **마케팅 지식을 많이 말하는 것**이 아니다.
일반 Claude가 자주 빠뜨리는 데이터 확인·판정 기준·파일 저장·검토·다음 행동을 한 흐름으로 묶는 데 있다.

따라서 현재도 중급 마케터에게는 실용적이다. 하지만 대중적인 플러그인으로 판단하려면 다음 셋이 먼저다.

1. 자연어 라우팅 95% 이상
2. 중단 복구를 포함한 단일 실행 완주율 90% 이상
3. 실제 마케터 15명 비교 테스트에서 시간 단축과 결과물 사용성 입증

이 셋과 설치본 새 대화 3종을 통과하면 잠정 83점에서 **현장 검증 85점 이상**으로 릴리스 판정을 바꿀 수 있다.
