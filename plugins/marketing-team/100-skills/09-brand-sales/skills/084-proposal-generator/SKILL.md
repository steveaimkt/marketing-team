# 084 제안서 작성

> 🔴 **`.pptx` 는 우리가 직접 굽지 않는다.** 내용은 여기서 만들고, **파일로 굽는 일은 공식 pptx 스킬에 넘긴다.**
> 공식 스킬이 안 깔려 있으면 **`.md` 로 내고 그렇게 말한다.** 대부분 이미 깔려 있고,
> 없을 때만 두 줄을 안내한다 — `/plugin marketplace add anthropics/skills` ·
> `/plugin install document-skills@anthropic-agent-skills`. ⛔ 설치를 강요하지 않는다.
> ⛔ **`.pptx` 라고 적어 놓고 `.md` 를 내지 않는다.** 못 구우면 **계획에서 미리 형식을 바꾼다** (`AI-마케터` §산출물 형식도 묻고 정한다).

문의·RFP 한 건을 **수주 논리가 관통하는 맞춤 제안서**로 바꾼다. 검증 파이프라인 v2 계승: RFP 분석 → Win Theme → SPARK-6 목차 → 섹션 초안. "우리 회사 소개서" 재탕이 아니라, 고객의 평가 기준에 역산해 쓴다.

## Contract
1. 제안서는 반드시 **RFP·문의 분석 이후**에 작성된다 — 요구사항·평가 기준·Pain Point 3개 이상을 추출하기 전에는 본문을 쓰지 않는다.
2. Win Theme(수주 전략 메시지) 3개가 먼저 확정되고, 모든 섹션 초안에 어느 Theme을 뒷받침하는지 태깅된다.
3. 목차는 SPARK-6 구조(문제 재정의→기회→해법→실행→증거→투자 대비 효과)를 따르며, 고객 문의 문구를 최소 2회 직접 인용해 맞춤성을 증명한다.
4. 모든 섹션 제목은 Action Title(인사이트+데이터 문장형, 15~35자)로 쓴다 — "회사 소개" 같은 Topic Title 금지.
5. 가격·조건·성과 표현이 포함된 최종본은 compliance-gate 를 통과한 것만 전달된다 (보장성 표현·근거 없는 수치 전수 검사).
6. **디자인은 게이트 통과 뒤에만 시작한다.** 문서에서 걸러야 할 문구를 슬라이드에 옮기면 회수 비용이 커진다.
7. **문서에서 멈추지 않는다** — 게이트를 통과하면 슬라이드와 `.pptx` 까지 만들어 파일 경로를 알린다. 디자인 방향은 앞 단계에서 확정된 값으로 채우고 **사용자에게 되묻지 않는다.**
8. **슬라이드는 `brand-templates/디자인시스템/tokens.css` 값만 쓴다** — 색·서체·크기를 제안서마다 새로 정하지 않는다. 표지·목차·내용 세 장의 골격이 고정돼 있고 (Phase 8-b), 본문 6장 중 최소 3장은 도형으로 그린 도식을 담는다 (Phase 8-c).

## 게이트 (대화형에서만 멈춘다)

> 사람이 부르면 아래에서 멈춰 답을 받는다. 대시보드·cron 에서는 기본값으로 완주하고
> 산출물에 "물어보지 못해 기본값으로 갔다"를 밝힌다.
> ⚠️ **규제 검사와 다른 것이다.** 그쪽은 마지막에 자동으로 돌고 사람을 안 부른다.
> 걸리면 ⛔ 로 전달을 막을 뿐이다. 아래는 **사람에게 묻는 자리**다.

| 멈추는 곳 | 묻는 것 | 기본값 (답 없으면) |
|---|---|---|
| Phase 1 | RFP·문의가 없으면 묻고 멈춘다 | **제안서 틀**을 먼저 낸다 (목차·필수 항목) + **D3 계약** · 부족 항목은 `[확인 필요]` |
| Phase 3 ⏸ | **Win Theme 승인 전에는 목차·본문을 쓰지 않는다** (여기가 뼈대다) | 묻고 멈춘다 |
| Phase 8 앞 | **디자인 방향은 묻지 않는다** — 장수·독자·분위기·내용을 앞 단계 값으로 채운다. 다만 고객이 지정한 템플릿·브랜드 서식이 있으면 그것을 묻는다 | 앞 단계 값으로 진행 |
| Phase 9 뒤 | "제안서·슬라이드·`.pptx` 입니다. 보낼까요?" | 파일까지 산출 · **발송하지 않는다** |

## Phases
1. **입력 분석 (RFP/문의)** — RFP 파일 또는 문의 내용에서 추출: 요구 과업 목록 · 평가 기준(배점 있으면 배점순) · 예산·일정 제약 · 행간의 Pain Point 3개 이상. RFP가 없는 구두 문의면 문의 문장을 같은 틀로 구조화하고 부족 항목은 [확인 필요] 태그.
2. **Win Theme 도출** — Pain Point ↔ 우리 강점(brand/profile.md)을 교차해 수주 전략 메시지 3개를 만든다. 각 Theme = "고객의 {문제}에 우리는 {차별 근거}로 답한다" 1문장 + 지지 증거 1개.
3. ⏸ **Win Theme 승인** — 3개 Theme과 분석 요약을 제시하고 사용자가 확정/수정한다. 승인 전 목차·본문 작성 금지 (여기가 제안서의 뼈대다).
4. **SPARK-6 목차 설계** — 6부 구조로 목차를 만들고 각 섹션에 ① Action Title ② 담을 핵심 메시지 1줄 ③ 대응 Win Theme 번호 ④ 근거 자료를 배정한다. 평가 기준 배점이 높은 항목에 분량을 비례 배분.
5. **섹션 초안 작성** — 섹션별로 S-E-P 설득 구조(Story 공감 → Evidence 출처 있는 근거 → Promise 행동 유도)로 초안을 쓴다. 수치는 출처·기준 시점 병기, 없는 수치는 [추정] 태그. 고객 문의 문구 인용 2회 이상 포함.
6. **커버레터 작성** — 제안서 요지 3줄 + 다음 스텝 제안(미팅·데모)을 담은 발송용 커버레터 1통 (제목 2안).
7. ⏸ **compliance-gate 통과** — gates/compliance-gate.md 3 STEP 실행. "100% 보장" "최저가" 등 보장성·최상급 표현 검사 후 판정 블록을 부착한다. **⛔ 가 뜨면 여기서 멈춘다 — 디자인으로 넘어가지 않는다.** 통과하지 못한 문구가 슬라이드에 박히면 회수 비용이 문서보다 크다.
8. **디자인 발주** — 사용자에게 방향을 되묻지 않는다. 위에서 이미 확정된 값으로 발주문 4칸을 **자동으로 채워** 디자인 도구에 넘긴다.
   | 칸 | 어디서 가져오나 (되묻지 않는 이유) |
   |---|---|
   | **만들 것·장수** | SPARK-6 섹션 수에서 센다 · 표지 1 + 목차 1 + 본문 6 + 마무리 1 = **9장** 기본 |
   | **읽는 사람** | Phase 1 의 평가 주체 (심사위원회 / 구매 담당 / 대표 결재) — "외부 고객"으로 뭉뚱그리지 않는다 |
   | **분위기** | 고객 성격에서 정한다 · 공공·입찰 → 차분한 뉴트럴 / 스타트업·신사업 → 굵고 단호한 / 브랜드·리테일 → 잡지 같은 / 발표 현장 → 어두운 발표용 |
   | **내용** | 각 장 Action Title 을 그대로 넣는다. 미확정 수치·날짜는 `[ ]` 로 비운다 — **지어내지 않는다** |
   결과는 **편집 가능한 캔버스 링크**로 나온다. 고칠 때는 스킬을 다시 부르지 않고 *"3장 제목 바꿔줘"* 처럼 말하면 같은 링크에 반영된다.

   **8-a. 디자인 시스템 · 슬라이드가 쓰는 값**

   > 정본은 `brand-templates/디자인시스템/tokens.css` 다. 「여기 없는 값은 만들지 않는다」가 슬라이드에도 그대로 걸린다.
   > ⚠️ **`.pptx` 에는 CSS 가 없다.** `var(--ink)` 를 쓸 수 없으므로 `python-pptx` 가 **도형마다·글자마다 값을 직접 박는다** —
   > `RGBColor(0x2A, 0x2A, 0x28)` · `Pt(34)` · `font.name = "Pretendard"`. 안 박으면 파워포인트 기본 테마가 그대로 나온다.

   | 쓰는 자리 | 토큰 | 값 |
   |---|---|---|
   | 슬라이드 바탕 | `--paper` | `#F3F3F2` |
   | 올라온 면 · 카드 | `--paper-card` | `#FFFFFF` |
   | 가라앉은 면 · 표 머리 행 | `--paper-sunk` | `#EBEBEB` |
   | 제목·본문 글자 | `--ink` | `#2A2A28` |
   | 보조 글자 | `--ink-mut` | `#444444` |
   | 캡션·출처 | `--ink-faint` | `#848383` |
   | 지난 것·비활성 | `--ink-fade` | `#AFAFAC` |
   | 헤어라인 | `--line` | `#EBEBEB` |
   | 굵은 구분선 | `--line-strong` | `#444444` |
   | 강조 면 (Win Theme 띠) | `--sand` | `#E0CCBE` |
   | 강조 글자·막대 | `--olive` | `#747264` |
   | 사람이 채울 `[ ]` 자리 | `--mark` | `#EBFF2C` |
   | 좋음 · 나쁨 · 주의 | `--up` · `--down` · `--warn` | `#3F5F4A` · `#7A3B36` · `#6B5A2E` |

   | 글자 | 토큰 | `Pt()` |
   |---|---|---|
   | 서체 | `--ff` | Pretendard (없으면 Apple SD Gothic Neo · Malgun Gothic) |
   | 표지 제목 | `--t-h1` | **34** |
   | 장 제목 (Action Title) | `--t-h2` | **20** |
   | 소제목·라벨 | `--t-h3` | **15** |
   | 본문 | `--t-body` | **15** |
   | 출처·읽기 한 줄 | `--t-small` | **13** |
   | 각주·태그·쪽번호 | `--t-tiny` | **12** |
   | 숫자 하나를 크게 | `--t-kpi` | **34** |

   여백은 `--sp-4` **20** 을 기본 간격으로, 카드 사이는 `--gap-card` **20**, 카드 모서리는 `--r-l` **13** 으로 둔다.
   토큰의 px 숫자를 `Pt()` 에 **그대로** 넣는다 — 슬라이드라고 키우거나 줄이지 않는다.

   ⛔ **새 색을 만들지 않는다.** 위 표에 없는 값은 쓰지 않는다 — 고객사 로고 색도 슬라이드 색으로 승격하지 않는다.
   ⛔ 파워포인트 기본 테마(맑은 고딕 · 제목 파랑 · 도형 파란 채움과 그림자)를 그대로 두지 않는다. 안 덮으면 그것이 나온다.
   ⛔ 색만으로 의미를 싣지 않는다 — 기호(▼ ★ ⛔)를 함께 쓴다.

   **8-b. 슬라이드 3장 · 표지 · 목차 · 내용**

   세 장의 골격을 고정한다. 본문 S1~S6 은 ③ 을 그대로 여섯 번 반복한다.

   **① 표지** — 바탕 `#F3F3F2` · 왼쪽 끝에서 위아래로 `#E0CCBE` 세로 띠 하나.
   | 담는 것 | 크기·색 |
   |---|---|
   | 제안 제목 = **고객의 문제 한 문장** (우리 회사 이름 아님) | `Pt(34)` · `#2A2A28` · 왼쪽 정렬 |
   | 고객명 · 과업 한 줄 | `Pt(15)` · `#444444` |
   | 제출일 · 제출처 · 제안사명 (맨 아래 한 줄) | `Pt(12)` · `#848383` |
   ⛔ **표지에 회사 소개를 넣지 않는다** — 연혁·조직도·수상 이력·고객사 로고 나열. 그것은 S5 증거의 재료지 표지가 아니다.
   ⛔ 스톡 이미지·그라데이션·사진 배경을 깔지 않는다. 제목을 가운데 정렬로 띄우지 않는다.

   **② 목차** — 이 제안서에 **실제로 있는 SPARK-6** 여섯 줄. 지어낸 목차가 아니다.
   | 줄 | 무엇이 들어가나 |
   |---|---|
   | S1 문제 재정의 | 번호 + 그 섹션의 Action Title `Pt(20)` `#2A2A28` + 대응 `WT1` `Pt(13)` `#747264` |
   | S2 기회 / S3 해법 / S4 실행 / S5 증거 / S6 투자 대비 효과 | 같은 골격으로 다섯 줄 더 |
   줄 사이는 `#EBEBEB` 헤어라인. **평가 기준 최고 배점에 대응하는 줄 하나만** `#E0CCBE` 로 옅게 깐다 — 심사위원이 자기 배점표를 목차에서 찾는다.
   ⛔ "인사말 · 회사 소개 · 사업 개요 · 맺음말" 같은 **범용 목차를 쓰지 않는다.** 목차가 SPARK-6 과 어긋나면 본문이 아니라 목차를 고친다.
   ⛔ 목차에 없는 장을 본문에 끼워 넣지 않는다. 장 번호와 목차 번호가 발표 중에 어긋나면 신뢰를 잃는다.

   **③ 내용** — 본문 한 장의 표준 레이아웃. 위에서 아래로 넷.
   | 자리 | 무엇이 | 크기·색 |
   |---|---|---|
   | 1 · 맨 위 | Action Title 한 줄 (한 장에 메시지 하나) | `Pt(20)` · `#2A2A28` |
   | 2 · 제목 아래 | `#EBEBEB` 헤어라인 1개 | — |
   | 3 · 가운데 | **도식 또는 표 한 개** (8-c) · 출처·기준 시점을 바로 아래 | 캡션 `Pt(13)` · `#848383` |
   | 4 · 맨 아래 | 「읽기 — …」 한 줄 · 이 장에서 무엇을 읽어야 하는지 | `Pt(13)` · `#848383` |
   오른쪽 위 구석에 Win Theme 태그 `WT1` `Pt(12)` `#747264`. 미확정 값은 `#EBFF2C` 로 칠한 `[ ]` 로 남긴다.
   ⛔ **한 장에 메시지 둘을 넣지 않는다.** 둘이면 두 장이다.
   ⛔ 글머리표 일곱 줄로 장을 채우지 않는다 — 그것은 문서지 슬라이드가 아니다 (8-c).

   **8-c. 도식화 · `python-pptx` 로 그린다**

   ⚠️ `python-pptx` 는 `add_shape` 로 **도형을 직접 그린다** (`docs/차트-규격.md §3-3`).
   워드는 도식을 표로 대신하지만 **PPT 는 진짜 도형과 연결선으로 그린다.** 표로 대신하지 않는다.

   | 도식 | 어느 장 | 그리는 법 |
   |---|---|---|
   | **문제 → 해결 흐름** | S1 · S3 | `MSO_SHAPE.CHEVRON` 넷을 가로로 이어 붙인다 — 「고객 문제 → 원인 → 우리 해법 → 고객이 얻는 것」. 앞 둘은 채움 `#EBEBEB` 글자 `#444444`, 뒤 둘은 채움 `#E0CCBE` 글자 `#2A2A28` — 문제 쪽과 해법 쪽이 색으로 갈린다 |
   | **일정 타임라인** | S4 | 가로 직선 하나를 `add_connector(MSO_CONNECTOR.STRAIGHT)` 로 긋고(`#444444`) 그 위에 `MSO_SHAPE.OVAL` 로 마일스톤을 찍는다. 점마다 위에 시점, 아래에 담당·할 일. 지난 것 `#AFAFAC` · 앞으로 올 것 `#2A2A28` · 기한 밖 `#7A3B36` 에 ▼ |
   | **비용 구성** | S6 | `MSO_SHAPE.RECTANGLE` 을 폭 비율대로 이어 붙인 가로 100% 누적 막대 하나. 큰 항목부터 `#747264` 에 투명도를 올려 가며 옅게, 예비비 칸만 `#EBEBEB`. 칸 안에 항목명·비율, 총액은 막대 오른쪽 끝에 `Pt(34)` |
   | **판단 분기** (필요할 때) | S4 · 부록 | `MSO_SHAPE.DIAMOND` 가 판단, `MSO_SHAPE.ROUNDED_RECTANGLE` 이 행동, 화살표 연결선은 `#848383`. 되돌아오는 선은 긋지 않고 「①로」라고 글자로 적는다 · 한 화면에 분기 일곱까지 |

   ⛔ **글자만 있는 제안서 장은 슬라이드가 아니다.** 본문 6장 중 **최소 3장**은 위 도식 하나를 도형으로 그린다.
   못 그리는 내용이면 표로 내리고 그 장은 지운다 — 문단을 붙여 장수를 채우지 않는다.
   ⛔ 도형 채움·선·글자에도 8-a 색만 쓴다. 도형을 그린 뒤 채움과 선을 **명시로 덮는다.**
9. **PPTX 출력** — 디자인 도구는 캔버스까지만 낸다. **여기서 멈추지 않고 발표용 `.pptx` 파일까지 만들어 경로를 알린다.** 사용자가 따로 요청할 때까지 기다리지 않는다 — 제안서는 보내야 끝나는 물건이다. PDF 가 필요하면 같은 자리에서 함께 낸다.
   > 디자인 도구가 연결돼 있지 않으면 **여기서 실패로 처리하지 않는다.** 8단계의 발주문을 그대로 화면에 내고
   > *"디자인 도구를 연결하면 이 문장으로 바로 슬라이드가 나옵니다"* 를 붙인다 (`docs/데이터-가져오기.md` 참조). 문서 산출물은 이미 완성돼 있다.

10. **파일로 남긴다** — 위 산출물을 아래 「⛔ 착지」의 세 파일로 저장하고 경로를 알린다. 화면에만 띄우고 끝내지 않는다 — 마케터가 다음 날 다시 열 수 있어야 한다.
   > 쓰기 권한이 없으면 **실패로 처리하지 않는다.** 산출물은 그대로 화면에 내고 맨 아래에 "`outputs/{날짜}/084-proposal-generator/084-proposal-generator.pptx` 로 저장하려 했으나 권한이 없어 남기지 못했습니다" 를 적는다. 못 한 일을 못 했다고 말하는 것도 산출물의 일부다.

> ⛔ **착지 · 세 파일로 쓴다**
> · 발표 → `outputs/{날짜}/084-proposal-generator/084-proposal-generator.pptx`
> · 회람 → `outputs/{날짜}/084-proposal-generator/084-proposal-generator.docx`
> · 본문 → `outputs/{날짜}/084-proposal-generator/084-proposal-generator.md`
> 경로를 새로 만들지 않는다. 위 줄을 그대로 쓰고 `{날짜}` 만 오늘로 바꾼다.
> 아티팩트·스크래치패드·화면 출력은 착지가 아니다. **파일이 없으면 안 한 것이다.**
> **형식** · 만들 수단이 있으면 `.pptx` 와 `.docx`, 없으면 **`.md` 개요로 쓰고 첫 줄에 밝힌다**. 마크다운을 `.pptx`·`.docx` 로 이름만 바꾸지 않는다 (`docs/공통규약.md §H`)
> 🔴 **`.pptx` 와 `.docx` 는 우리가 직접 굽지 않는다.** 내용은 여기서 만들고 **파일로 굽는 일만 앤트로픽 공식 `document-skills`** 에 넘긴다.
> 안 깔려 있으면 **`.md` 로 내고 그렇게 말한다** — `/plugin marketplace add anthropics/skills` · `/plugin install document-skills@anthropic-agent-skills`. ⛔ 설치를 강요하지 않는다.

## Anti-Patterns
- **회사 소개서 재탕** — 우리 자랑 순서(연혁→조직→실적)로 쓰지 않는다. 고객 문제 재정의가 항상 첫 섹션.
- **분석 없이 집필** — RFP를 읽는 척만 하고 범용 제안서를 내는 것. 평가 기준·Pain Point 추출물이 없으면 Phase 2로 못 간다.
- **Topic Title** — "사업 이해", "수행 방안" 같은 명사형 제목 금지. 모든 섹션 제목은 데이터·인사이트가 담긴 문장형.
- **Win Theme 미관통** — Theme을 서두에만 쓰고 본문 섹션과 태깅 연결이 없으면 장식이다. 태깅 안 되는 섹션은 삭제 후보.
- **근거 없는 수치 확정** — 시장 수치·성과 수치를 출처 없이 본문에 박으면 게이트 차단 대상. [추정]·[확인 필요] 태그로 구분한다.
- **디자인 방향을 되묻기** — "어떤 톤으로 할까요?" 라고 물으면 앞의 8단계가 헛일이 된다. 장수는 목차에서, 독자는 평가 주체에서, 분위기는 고객 성격에서 **이미 정해져 있다.** 되물어도 되는 것은 고객이 지정한 템플릿·브랜드 서식뿐이다.
- **캔버스에서 멈추기** — 링크만 주고 끝내는 것. 제안서는 **보내야 끝나는 물건**이라 `.pptx` 까지 나와야 완료다. 사용자가 "파워포인트로도 만들어줘" 라고 말하게 두지 않는다.
- **게이트 전에 디자인** — 걸릴 문구를 슬라이드에 옮기면 문서 한 줄 고치는 일이 8장 재작업이 된다. 순서를 바꾸지 않는다.
- **빈칸 채워 넣기** — 미확정 날짜·금액을 그럴듯하게 지어 슬라이드에 박는 것. `[ ]` 로 비워 두면 사람이 채운다. 채워진 숫자는 아무도 안 본다.
- **글자만 있는 슬라이드** — 문단과 글머리표만 얹은 장. 그것은 문서를 옮겨 붙인 것이지 슬라이드가 아니다. 본문 6장 중 최소 3장은 8-c 도식을 **도형으로** 그린다. 못 그리면 그 내용은 표로 내리고 장을 지운다.
- **PPT 도식을 표로 대신하기** — `python-pptx` 는 `add_shape` 로 도형을 그린다. 워드에서 표로 대신하는 규칙을 PPT 로 가져오면 흐름도 타임라인도 격자가 된다 (`docs/차트-규격.md §3-3`).
- **색을 새로 정하기** — 제안서마다 톤에 맞춰 색을 고르는 것. 색·서체·크기는 `tokens.css` 가 이미 정했고 8-a 표 밖의 값은 쓰지 않는다. 고객사 로고 색도 슬라이드 색으로 승격하지 않는다.
- **기본 테마 방치** — `.pptx` 에는 CSS 가 없어 안 박으면 파워포인트 기본값(맑은 고딕·제목 파랑·파란 도형)이 그대로 나간다. 도형마다 글자마다 값을 명시로 덮는다.
- **범용 목차** — "인사말 · 회사 소개 · 사업 개요 · 맺음말". 목차 한 장에서 이미 회사 소개서 재탕이 들통난다. 목차 여섯 줄은 이 제안서의 SPARK-6 Action Title 이어야 한다.

**Win Theme 3개를 승인받기 전에는 목차도 안 쓴다.** 여기가 제안서의 뼈대라
뒤집히면 전부 다시 쓴다. 순서를 지키는 게 가장 빠르다.

그 승인 하나만 하면 **나머지는 파일까지 알아서 간다.** 톤이나 장수를 다시 묻지 않는다 —
목차가 9장을 정하고, 평가 주체가 독자를 정하고, 고객 성격이 분위기를 정한 뒤라
물을 것이 남아 있지 않다. 색과 글자 크기도 묻지 않는다 — `tokens.css` 가 이미 정해 놨다.
마지막에 손에 남는 것은 `.pptx` 한 개다. 표지 · 목차 · 본문 여섯 · 마무리, 본문에는 도형으로 그린 도식이 들어 있다.

## 활용
- **B2B 서비스 수주**: 인바운드 문의 → 당일 Win Theme 승인 → 익일 제안서 발송. 086 미팅 노트가 있으면 Pain Point 추출 입력으로 재사용 (「세일즈파이프라인」 체인).
- **공공·대기업 입찰**: RFP 평가 배점표를 그대로 목차 분량 배분에 반영 — 배점 높은 항목이 얇은 제안서를 구조적으로 방지.
- **제휴·지원사업 파생**: 같은 파이프라인이 087(제휴 제안)·090(지원사업 서류)의 뼈대 — 분석 대상만 브리프/공고문으로 바뀐다.
- **급한 발표**: 문의 하나만 붙여 넣어도 게이트 통과한 `.pptx` 가 나온다. 슬라이드를 다시 짤 시간이 없을 때 캔버스 링크에서 문구만 고쳐 발표한다.
